智能日程 v1.3 测试报告

主动找问题：代码审查 + 畸形输入 fuzz + 探针表 + 静态检查，四条线并行
单测 49 / 49 通过 lint 0 error / 34 warning 查出问题 14 个 已修 11 个 保留 3 个（有原因）

怎么测的

  • 读代码：把监听链路、保活、数据层、大模型解析全过一遍，盯状态机和异常路径。
  • 畸形输入压测：2000 条随机生成文本 + 病态串（5000 个 1、1点×2000、【】×2000），要求不抛异常、不卡死（每次 < 2s，实测都在 10ms 内）。
  • 探针表：40 条真实语气的句子跑一遍，把 日期来源 / 置信度 / 标题 / 地点 列成表格人眼过——这一步抓到的错误比断言多得多。
  • 静态检查：lint 分类看，不只看 error 数量。

P0 · 直接影响使用

P0中文数字时间完全不识别已修

现象
「下午三点到五点值班」→ 整条解析失败，返回 null
根因
时间正则只写了 \d{1,2}，只认阿拉伯数字。"三点""两点半""八点"一个都不认。
影响
中文群通知里"下午三点"比"下午3点"还常见。这是"识别不到通知"的主要来源之一。
修法
加 RE_CN_TIME_CN 中文数字时间正则，复用已有的 cnToInt（支持 十一 / 二十三）。加 hasTimeContext() 上下文校验，避免把"一点小事"当成 1 点。
验证
「明天下午三点半在体育馆集合」→ 15:30，85 分，自动入库

P0大模型兜底会建出两条重复日程已修

现象
开了大模型兜底后，同一条通知在列表里出现两条日程。
根因
本地结果先 insert 一条"防止网络失败丢数据"，大模型结果回来后又 insert 一条。
本该由 existsSimilar 挡住，但它按标题完全相等 + 时间 ±5 分钟判断——大模型会改写标题（"开会"→"部门例会"），所以挡不住。
修法
persist() 改为返回行 id；大模型结果更好时用 replaceId 原地 update 那一行，并先 ReminderScheduler.cancel 撤掉旧提醒再按新时间重排。
验证
代码路径审查 + 编译通过；无网络环境，未做真机联调（见文末）。

P0通知回调没有异常保护已修

现象
偶发"过一阵子就再也收不到通知了"，重启手机才好。
根因
onNotificationPosted 里直接跑正则和时间解析，没有任何 try/catch。通知正文来自任意第三方应用，内容不可控；一次异常抛出去，系统会把这个 NotificationListenerService 判定为异常，之后可能不再回调。
修法
入口包 try/catch Throwable，异常写进抓取日志（"处理通知时出错：XXX"），服务继续活着。
验证
fuzz 2000 条随机文本 + 病态串，解析器本身已确认不抛异常，这层是兜底。

P0取消类通知被建成日程已修

现象
「明天不开了」→ 建出一条标题为"不开了"的日程，挂在待确认里。
根因
解析器只管抽时间，完全没管语义。
修法
加 isCancellationNotice()：命中"取消/作废/停办/不开了"等词直接返回 null。
关键分寸：如果同时出现变更词（改到 / 推迟到 / 延期 / 顺延），说明是"改时间"而不是取消，"取消原定时间，改到后天3点"仍要解析出后天3点。
验证
5 条取消句式全部返回 null；「会议改到 10月25日 16:30」仍正确解析成 16:30。

P1 · 明显影响体验

P1「本周五」被报成"没说清是哪一周"已修

现象
「本周五开会」弹警告："原文只写了「本周五」，没说清是哪一周"——用户明明写得很明确。
根因
resolveWeekday() 只对"下下/下/上"做了专门分支，"本/这"落到通用分支；通用分支里 delta == 0（今天就是周五）被当成"有歧义"。
修法
给"本/这"单开分支（明确指定本周，不推下周、不算 vague）；通用分支的歧义判定改成 delta >= 4——只有"今天说周二"这种情况才真有歧义。

P1地点抽到了时间残渣已修

现象
「明天9点到12点在体育馆体检」→ 地点 = "12点在体育馆"
「会议改到16:30」→ 地点 = "16:30"
根因
地点正则用"在/到"作前缀，"9点到12点在体育馆"里的第一个"到"被当成了地点前缀。
修法
cleanLoc() 开头循环剥前导时间片段（12点 / 16:30 / 9点到12点，阿拉伯数字和中文数字都覆盖）和前导介词；剥完为空就判定"整个候选都是时间，不是地点"。
特意没有用"以数字开头就否决"——那会误杀"302会议室""3号楼"。
验证
上面两例分别得到 "体育馆" 和 无地点。

P1关了保活开关，常驻提示还在已修

根因
服务返回 START_STICKY，被系统杀掉后会重新拉起并再次 startForeground，但 onStartCommand 里没检查用户开关。而且原来的"关闭"逻辑写在 onDestroy 里调 stopSelf()——进程被 kill 时 onDestroy 根本不会执行，属于无效代码。
修法
onStartCommand 开头检查 Prefs.keepAlive，关了就 stopForeground + stopSelf 并返回 START_NOT_STICKY；删掉 onDestroy 里的无效调用。

P1标题被吃出残渣已修

现象
「周五前提交材料」→ 标题 "前提交材料"
「下午三点到五点值班」→ 标题 "到五点值班"
「2026/10/25 9:00-11:00 培训」→ 标题 "培训"（这条是对的）
根因
日期/时间的匹配区间没有覆盖"尾巴"："周五前"的"前"、"三点到五点"的后半段都留在正文里。
修法
新增 extendWeekTail()（吃掉 前/之前/以前）和 RE_TIME_RANGE（把区间后半段并进时间 span）。

P1大模型解析的三个独立缺陷已修

①
s.trim().replace('T', 'T') —— 把 T 换成 T，完全无操作，明显是笔误（本意可能是归一化 ISO 的 T 分隔符）。已删。
②
模型返回中文日期「2026年10月25日 20:00」时，四种 yyyy-MM-dd 格式全部失败 → 整条丢弃。已加中文日期兜底。
③
用户把完整地址粘进来（.../v1/chat/completions）会被再拼一次，变成 .../chat/completions/chat/completions，报 404 且没有任何提示。已判断后缀，避免重复拼接。

P1排提醒没有异常兜底已修

根因
canScheduleExactAlarms() 在个别 ROM 上会说谎（检查通过，真排的时候抛 SecurityException），而 setExactAndAllowWhileIdle 外面没有保护。
修法
精确闹钟失败自动降级到非精确 setAndAllowWhileIdle；cancel 也包上 runCatching。

P2 · 静态检查捞出来的

问题说明处理
死资源glass_fill_soft 在改成蓝色后没人引用了已删
死代码ServiceHealth 里的 SDK_INT < M 判断，minSdk 26 之下恒为 false已删（连 import 一起）
列表全量重绑每次勾选、每次 onResume 都 notifyDataSetChanged()，所有卡片（含 5 层亚克力背景）重绘一遍内容没变就直接 return
卡片背景反复重建setBackgroundResource 每次 bind 都调，会重建 Drawable用 tag 记住当前背景，变了才换
Overdraw列表项根布局自己画背景，主题也画了一层窗口背景保留
Overdraw 为什么不修：亚克力面板本身就是"半透明层 + 噪点 + 高光"叠出来的，多一次合成是这套视觉的固有成本。 真机上如果滚动明显掉帧，第一件事是把 noise_tile.png 那层去掉试试——它是唯一可以牺牲的质感来源。

发现的但本轮没修

问题为什么不修
「1小时后」「半小时后」「月底前」不识别需要新的相对时间规则族，和现有"日期 + 钟点"模型不同，改动面大，先记录。
「周三或周四」只取第一个，且"周四"会被当残渣清掉属于"一段多日期"的已知限制。要修得引入候选集 + 让用户选，是交互设计问题不是解析问题。
整句只有一个日期时，标题会只剩"上午"原文确实没有事件名（"本周日上午"），没有信息可抽。当前兜底是退回原文，可接受。
对话框仍是 Material 纯白要改得重做 materialAlertDialogTheme 背景，有把系统弹窗搞花的风险，留到下一轮单独做。
