一、怎么造出"来自微信"的通知

这里有个绕不开的坎：App 判断来源用的是 StatusBarNotification.packageName， 那个值由系统按安装包填，改不了。想验证「只分析微信 / QQ」这条规则，就必须让通知的包名 真的是 com.tencent.mm。

所以写了一个极小的通知模拟器（tools/notify-sim/，纯 Java、零依赖）， 打包时把 applicationId 设成 com.tencent.mm， 再出一份 com.example.notifysim 的变体当对照组。测试语料的中文直接硬编码在代码里， 用 --ei case N 选第几条 —— 走 shell 传中文会被编码搞坏。 

adb shell am start -n com.tencent.mm/com.terry.notifysim.PostActivity --ei case 3
adb shell am start -n com.example.notifysim/com.terry.notifysim.PostActivity --ei case 20
两台设备上的实际情况：模拟器里已经装了真 QQ 9.3.35（今天 09:40 装的）， 所以测试包只能用微信的包名，避开了 QQ 避免覆盖。测完两个测试包都已卸载， 真 QQ 没动过。

三、三个关键验证点

1. 标题真的不再参与识别了

这是 v1.19 的核心改动，也是最容易"以为改了其实没改"的地方。#16 #17 #18 三条的标题里 日期时间俱全，正文都够长、只是没有时间：

  • 标题「明天下午3点开会」+ 正文「收到请回复」 → 拦
  • 标题「10月25日 部门会议 15:00」+ 正文「好的收到」 → 拦
  • 群名「12.31」+ 正文「稍后再说吧」 → 拦

任何一条只要标题的日期还被使用，就一定会建成日程。三条全拦，说明 SegmentPicker.pick() 拿不到标题这件事，在真实管道上确实生效了。

测试过程里踩了自己的坑：最早这几条的正文写的是空字符串， 结果在「文本太短」那一步就被拦了 —— 通过了，但根本没走到标题逻辑。 这种"通过得不明不白"最危险。改成正文非空但仍无时间之后，才真正测到。

2. 应用白名单是硬拦截

#20 的内容和 #1 一模一样（完全该建），唯一的区别是包名不在白名单里。 它被拦在第一次判断：连正则都没跑。这说明"只分析微信/QQ"不是靠内容过滤 碰巧拦住的，而是真的在入口就挡了。

3. 去重两层都生效

#19 与 #1 内容完全相同，日志给的是「已经有一条一样的日程了」（Repo.existsSimilar）。 短时间内的重复还会更早被内存去重拦下（「10 分钟内处理过同样内容」）。

四、测出来的一个问题（未修）

群聊多消息时，标题会把几条消息拼在一起。
#2 的两条消息「张三：后天上午9点在图书馆三楼开会」和「李四：收到」， 建出来的标题是 开会李四:收到。

日期、时间、地点都对，只是标题不干净。原因：标题生成时把所有候选段拼起来， 而 RE_SPEAKER 只剥掉了第一个「张三：」前缀，后面的「李四：」被当成了内容。

微信/QQ 的群通知经常带多条消息，所以这个会比较常见。 没顺手改是因为它牵动所有日程的标题生成，属于另一件事 —— 要改的话建议单独一轮， 先定清楚"群聊标题取哪一条"（第一条？带事件词的那条？最长的那条？）。

另外两个观察

  • #9 的日志措辞：「看懂了是条日程，但没找到可用的日期时间」—— 这是 looksLikeSchedule 判为像日程、而解析器没解析出来的分支，结论正确（拦了）， 但说明"收到收到"这种词被当成了日程线索，属于粗筛偏松，不影响结果。
  • #6 的标题「明天下午3」：正文只有时间没有事件，标题只能截取残渣。 这和"正文位置不过滤纯时间"是同一个取舍 —— 宁可标题难看，也不漏掉真实的待办。

六、结论

筛选链路在真实通知管道上全部符合预期：6 条该建的都建对了日期， 14 条该拦的一条都没漏。标题不参与、白名单硬拦截、两层去重这三件事都有独立证据， 不是靠"看起来没出问题"推断的。

唯一发现的瑕疵是群聊多消息时标题会拼接（开会李四:收到）， 不影响日期和是否建日程，但观感不好 —— 修它需要先定标题的取舍规则，单独一轮处理。
