# 智汇日程（SmartSchedule）

把通知栏里的**群公告、作业 ddl、培训通知**自动变成日程；也能手动粘一段文字让应用识别。

- [GitHub Releases](https://github.com/terry0110/smart-schedule/releases) —— 下载最新 debug APK（仓库不提交 APK）
- 完整 Android 工程，Android Studio 打开即可编译

**给用的人看**：`dist/USER-GUIDE.md`（安装、授权、日常操作、排查）。
**给接手改代码的人（或 AI）看**：`docs/DEVELOPER-GUIDE.md`（环境、打包签名、代码地图、
改代码的常见任务、已知限制、上机验证命令）。
下面这份是开发/迭代记录。

### v1.46 —— 入库前冲突确认

### v1.44 —— 归档日志 + 左侧多选 + 清理重复日程

**列表行的两个框换了语义：**

- **最左：多选框，常驻**。点它进入多选并选中这一条，再点切换；顶部全选/删除照旧。

- **最右：归档**。点一下这条就从主列表消失，进「归档日志」，不再表示"已完成"。

**归档（DB v9）：**

- `events` 加 `archived` 字段；老数据里 `done=1` 的升级时自动搬进归档
- 归档会停闹钟、撤掉通知栏里的提醒和待确认，但**不删数据**
- 顶部新增归档入口；归档页每条可以恢复或删除。恢复会把 `done` 清零、重新排提醒

  日历同步不再推归档条目，已经写进日历的历史条目保留

**清理重复日程：**

- 设置 → 隐私与数据 → 「清理重复日程」
- `EventDeduper` 分组：宽松同题、地点不冲突、创建时间相差 ≤12 小时、日期相差 ≤3 天；
  同一天且都带钟点的必须落在 5 分钟内
- 先弹预览，确认后才删；预览会列出每组被删条目的日期，跨天组单独提示
  （避免把相邻两天的两场活动误当成重复）。每组保留最完整的一条
  （带具体时间 > 非待确认 > 最新创建），其余删除
- 删除前会重新读库校验：弹窗期间被改期的条目不删；被删副本独有的地点/备注
  会先补到保留项。提醒/通知按真正删掉的条目撤，日历条目一并删
- 分组用并查集求连通分量：A≈B、B≈C 但 A 与 C 创建时间差超过 12 小时时，
  三条仍会归成一组（旧贪心只会删 A/B，留下 C）

### v1.43 —— 同一条通知的截断版 / 完整版不再建两条

真实截图来自「贺老师盖章」那条通知：列表里出现三条 —— 全天截断版「…可以在」、
带「现有变」前缀的 15:00、完整版 15:00。三个原因逐个修：

1. **「现有变」不认**：它是「现时间有变」的少字写法，`RE_TIME_CHANGED` 现在把它也算进去
2. **全天版和带钟点版对不上**：通知被截断时只解析出日期（全天），完整版带时间；
   精确判重比"标题 + 时间"，09:00 和 15:00 永远不相等。新增 `EventMerge`：
   同一天、宽松同题、地点不冲突时，全天版与带钟点版视为同一条；
   完整版把全天版补成 15:00，**待确认也一并转正**
3. **标题差一个前缀**：`TextNorm.looseKey` 先剥掉「现时间有变 / 现有变」这类改期前缀，
   再做"短的是长的子串（≥6 字、长度差 ≤8）"的宽松同题判断

入库路径：`persist` 在 insert 之前查 `Repo.findMergeTarget`，命中就更新原条目、不新建；
旧提醒先撤，再按合并后的时间重排。

**验证**（模拟器）：

- 先发「端到端合并验证会议二，下周六（11月21日）」→ 全天 + 待确认
- 再发完整版「…下午3点」→ 同一条变成 15:00、`pending=0`，日程总数不变
- 再发「现有变，…下周日（11月22日）」→ 不会再建第三条；目标不唯一时走人工确认

**282/282 单测、lint 0 error**。新增 `EventMergeTest` 8 条 + `TimeChangedNoticeTest` 1 条。

**历史数据讲清楚**：旧版本已经建出来的重复条目**不会被自动删除**——自动批量删用户数据
需要单独的确认设计。这一版只保证"以后不再建"；列表里已有的重复可以长按多选删除。

### v1.42 —— 认得出「现时间有变」，不再拆成两条日程

真实案例：班委先发「下周六（11月21日）…盖章」，随后又发
「现时间有变，…下周日（11月22日）…盖章」。第二句没有「原定」，旧逻辑把它当新日程，
列表里出现两条互相矛盾的时间。

### v1.38 —— 改期没认准的，交给用户点一下

v1.37 只处理「信息完整」的改期：有旧时间、有新时间、能唯一匹配到一条。
但群消息经常是「原定四点的会推迟了」—— 缺新时间；或者同一个时间点有好几条日程。
以前这些情况只写一行日志，用户完全看不到，只会觉得"我说了改期，它没反应"。

现在补上**最小版人工确认**：

| 情况 | 行为 |
|---|---|
| 新时间有，目标不唯一 / 对不上 | 发「有一条改期需要确认」通知 |
| 有「原定…」但新时间没解析出来 | 同上，点开后打开编辑面板让用户自己补 |
| 没有对象的「会议提前了」 | **不发**，只记日志（问了也无从选起） |
| 候选为空 | **不发**，点开只能看到空列表 |

点开通知：候选按旧时间 ±30 分钟列出（和自动改期用同一个 `Repo.reviseCandidates`），
只有一条就直接进确认；确认框写清 old → new 和通知原文，上下午是推的会额外提示。
确认后 `Repo.reschedule` + 重排提醒 + 清旧提醒；缺新时间则复用编辑面板，
查重、完成状态、提醒重排全部走既有的 `saveEdit`，不另造一套。

**三条设计约束**：

- **不落库**。参数放在 PendingIntent extras 里，进程被杀也不丢；
  没被点开的询问没有保留价值，不值得为它加一张表（DB 仍是 v8）
- **通知 id 固定** `900_002`。一条改期一个 id 的话，一次群聊刷屏就能塞满通知栏，
  重演 v1.22 的限流事故（`muted=149/150`，连到点提醒一起被静音）
- **只问"有对象"的**。`Revise.worthAsking()` 是纯函数：`Unclear` 必须带旧时间才问。
  通知栏里每句含"提前/取消"的闲聊都弹一次，比漏改更烦人

**254/254 单测（+5）、lint 0 error**。新增 4 条 `ReviseTest`（信息不全时带旧时间、
什么该问什么不该问）+ 1 条 `NotificationIdsTest`（固定 id 不和回执撞）。

### v1.37 —— 认得出「改期」和「取消」

以前这两句话会变成四条互相矛盾的日程，现在第一条会被改、不会被复制：

```
明天下午四点在教学楼开会          → 建一条 20 日 16:00
原定明天下午四点的会议将提前至3点   → 把上面那条改到 15:00，不新建
原定明天下午四点的会议取消了      → 把那条标成「已取消」并停提醒，不删
```

- **新增 `parse/Revise.kt`（纯函数 + 19 条单测）**：靠句式判断，不靠解析结果。
  认「原定 X 改到 Y / 提前至 / 推迟到 / 顺延」和「取消 / 不开了 / 作废」；
  抽出旧时间和新时间两个锚点；新时间没写日期就从旧时间继承。
- **补了中文钟点**：「三点」现在按 3 点解析（解析器本身不认光秃秃的「三点」，
  实测 `parse("明天五点")` 会退化成"明天全天"）。
- **上下午推断**：「下午四点的会提前至3点」里那个 3 点，旧时间在下午就推成 15:00，
  并在处理日志里注明「上下午是按原时间推的」。
- **匹配策略宁严勿宽**：旧时间 ±30 分钟内找候选；只有一条就用，多条要用原文的字筛到
  唯一一条才动，筛不干净就不猜（返回 null，只记日志）。
- **取消只标记不删除**：DB v8 加 `revoked` / `revoke_reason`，列表显示红字「已取消」+
  删除线，提醒不再响。用户手动编辑保存后标记自动清除（他改过 = 他还认这条）。

  当成闲聊丢掉（它没有"具体安排"的措辞），取消完全没生效。修法是把 `Revise.detect`
  提到粗筛和闲聊判断之前，`isRevision` 为真就跳过这两道门。

**验证**：249/249 单测、lint 0 error。**端到端跑通了** —— 用 `tools/notify-sim`
（伪装成 `com.tencent.mm` 的最小工程）连发三条通知：建日程 → 改期 → 取消，

### v1.31 —— 消息去重：同一条通知不再建出两条日程

问题（真实场景）：同一条群通知会被反复处理 —— 微信群里每来一条新消息，
整个会话通知就重渲染一次；监听服务被系统回收再拉起时，系统还会把通知栏里
**已有的通知**重新回调一遍。旧判重（内存 10 分钟窗口 + 标题精确相等）挡不住：
进程一死内存表就空，标题差一个句号就漏，列表里出现两条一模一样的日程。

#### 三层判重

1. **内容指纹（L1 内存 / L2 落库）**：正文归一化（剥发送者/群名前缀、去空白标点
   表情、全角转半角）→ SHA-256 取 16 位指纹，**带会话维度**——判重只在同一会话内
   比对，两个群发同一条通知是两件事。L2 持久化在 `msg_seen` 表（12 小时 TTL +
   2000 行兜底），跨进程、跨重启有效；"插入即判重"借主键冲突天然互斥，并发也不漏
2. **事件级**：比对 `归一化标题 + 时间±5分钟 + 地点`，时间+地点+事件要素一致才合并
   ——标题差个句号不再是两条；但同时间同标题不同地点的两件事不会被误吞
3. 手动"检测"按钮照旧跳过判重（用户主动点就是想立刻看到结果），事件级兜底仍在

顺手修了一个真问题：归一化剥前缀时会把 "明天 15：00 开会" 的 "15：" 当成
发送者分隔符剥掉，时间直接丢——加了"冒号前后都是数字就是时间"的守卫，有单测钉死。

**189/189 单测（新增 18 条去重边界）、lint 0 error**。

### v1.25 —— 「全屏」的文案在说谎，改成符合实际

用户反馈两条：「选全屏，不进应用就触发不了」「稍后十分钟像没实现」。

**先在模拟器上把两条都实测了一遍，结论是功能都是好的，问题在说法：**

| 场景 | 实测结果 |
|---|---|
| 亮屏 + 应用在后台，到点 | 通知栏一条，**没有全屏页** |
| 息屏，到点 | 全屏页弹出 + 屏幕被点亮（`mWakefulness=Awake`，栈顶 `ReminderActivity`） |
| 点「稍后 10 分钟」 | 通知立刻清掉，闹钟排到 `+9m55s`（`dumpsys alarm` 里 `when=14:36:46`） |
| snooze 到点（息屏） | 重弹全屏页，页面显示的就是同一条 |

根因是一句 Android 的明文规定：

> the system UI may choose to display a heads-up notification, instead of
> launching this intent, **while the user is using the device**

也就是 `fullScreenIntent` 只在**息屏 / 锁屏**时真的启动全屏页；屏幕亮着、用户正在用手机时，
系统会把它降级成 heads-up 横幅。**「全屏」和「横幅」在亮屏状态下行为完全相同**，
两档的全部差别只在息屏时。

这不是 bug，是平台限制。要突破必须加 `SYSTEM_ALERT_WINDOW` 悬浮窗权限 ——
代价是用户得手动授权，而且会真的盖住一切。**这一版选择不改行为**，只把说法改准。

#### 改了什么

- 设置页三档说明按事实重写：「全屏」现在明写"息屏或锁屏时弹整页，你在用手机时系统会降级成横幅"
- 新增一行固定说明讲「稍后 10 分钟」的真实行为（推迟 10 分钟；到点若在用手机同样是横幅）
- 通知渠道 `remind_v2` 的 description 从「并弹出全屏提示」改成「息屏或锁屏时弹出全屏提示」
- **`RemindStyle` 的类注释原本写着"全屏页会盖在游戏上面"，是错的**，改成实测结论 + 平台限制说明
- README v1.23 的对比表格同步更正（原文"会盖住游戏"不成立）
- `USER-GUIDE.md` 三档表格同步更正

**165/165 单测**（无新增，本轮只动文案与注释）。

### v1.24 —— 删掉的日程，提醒不再赖在通知栏

起因：删掉一个日程之后，通知栏里那条"到点了"的提醒不一定跟着走。
它不会自己消失 —— 提醒通知带着 `setTimeoutAfter(一小时)`，用户得等满一小时。
在那之前点进去，日程已经没了。

#### 清理改成"自己记账"

原来每层删除逻辑都显式 cancel 一遍，另外还有一层兜底：进应用时回看系统
"通知栏里现在有什么"，把日程已经不在的撤掉。问题是**回看系统这件事不可靠** ——
查得到什么、什么时候更新，各版本各 ROM 都不一样，而且它只能回答"此刻还在"，
回答不了"我们发过、但日程已经没了"。

现在改成记账：

- 发出一条提醒 → 在 `Prefs.postedReminds` 记下这个日程 id
- 撤掉一条提醒 → 划掉
- 每次进应用补发时 → **账上有、但日程不在库里了** → 一律撤掉通知，顺手撤闹钟

好处是**路径无关**：日程是批量删的、在通知栏划掉的、清空数据清掉的，
还是进程被杀时没走到撤销那一步的，只要账上有、日程没了，就撤。
系统回看降级成第二道兜底，只用来收旧版本发出去的、账上没记的那些。

记账落盘，进程被杀也不丢。判断抽成纯函数 `orphanReminds(posted, alive)`，有单测钉着：
日程还在的一条都不能撤（误撤等于把还没处理的提醒悄悄弄丢，比留一条残留严重得多）。

#### 顺手补的漏洞

设置里的「删除所有本地数据」只撤了闹钟和"待确认"通知，**没撤到点提醒**；
而它紧接着的 `Prefs.clearAll()` 会把清扫用的账本一起清掉 —— 等于这条路后面
没有任何兜底。现在清空前逐条撤提醒。

#### 验证过程中踩到的坑（值得记一笔）

排查时一直用 `dumpsys notification` 看通知在不在，**被它骗了很久**：
它列出的"Notification List"里能看见 id，但真实通知栏（`cmd statusbar expand-notifications`
+ 看界面树）里根本没有 —— 已经撤掉的通知在 dumpsys 里还会留一阵。
结论：**判断通知在不在，只能看真实通知栏，别信 dumpsys。**

端到端验证（雷电 Android 9）：
提醒确实挂在通知栏 → 杀掉进程、删掉数据库文件（模拟日程消失且没走撤销路径）
→ 重新进应用 → 日志确认清扫命中 → 真实通知栏里那条提醒消失。

**165/165 单测**（新增 `OrphanRemindTest` 5 条）。

### v1.23 —— 提醒方式可选：全屏 / 横幅 / 静音

起因是一个具体的问题：**打游戏的时候会不会弹出来？**

当时的答案是"**会**"—— 以为 `setFullScreenIntent` 会盖住当前界面，游戏、视频一律被打断。
**这个判断后来被 v1.25 推翻了**：屏幕亮着时系统只给 heads-up 横幅，盖不住游戏；
真正会弹整页的只有息屏 / 锁屏状态。三档的设计本身没错（用户确实需要"弹不弹、响不响"
的选择），但"全屏会打断游戏"这个理由不成立。

所以加了「到点了怎么提醒我」三档，在设置页「提醒」区：

| 方式 | 亮屏时 | 息屏 / 锁屏时 | 响铃震动 |
|---|---|---|---|
| **全屏**（默认） | 横幅，**盖不住**前台界面 | 弹一整页 + 点亮屏幕 | 有 |
| **横幅** | 横幅 | 横幅（不弹页） | 有 |
| **静音** | 只往通知栏放一条 | 只往通知栏放一条 | 无 |

> ⚠️ 这张表在 v1.23 里写的是「全屏 = 会盖住游戏」，**不成立**。v1.25 实测更正，详见上一节。

三档都保留「知道了」「稍后 10 分钟」两个按钮 —— 静默模式也得能一键处理掉。

#### 实现上两个绕不开的点

**① 静音必须是独立渠道。** 通知渠道的声音、震动是**创建时固定**的，改不了；
同一个渠道做不到"有时响有时不响"。所以静音档走 `remind_quiet`（IMPORTANCE_LOW）。

**② 横幅 = 同渠道 + 不挂全屏意图。** 横幅和全屏用同一个 `remind_v2` 渠道
（一样响铃震动），区别只在**挂不挂 `fullScreenIntent`**。挂不挂是确定性的：
选了横幅就绝不会盖住游戏，不用赌系统判不判。

#### 设置项的处理

- **点选立刻生效**，不用按「保存」——用户改这个的动机往往是"刚才被弹烦了"
- 选中那档的说明文字跟着变，尤其写明"会不会打断游戏"
- 存下来的数字认不出来时**退回全屏**，不是静音。退回静默的话用户会以为应用坏了（到点一声不响）

#### 设备实测（dumpsys 证据）

| 档位 | 活动通知的真实属性 |
|---|---|
| 横幅 | `channel=remind_v2 pri=2 category=alarm`，`fullscreenIntent` 全为 **null** |
| 静音 | `channel=remind_quiet pri=-1 category=reminder` |
| 全屏 | 带 `fullscreenIntent`，息屏后 `ReminderActivity` 在栈顶且 `mWakefulness=Awake` |

**160/160 单测**（新增 `RemindStyleTest` 5 条，钉住"只有全屏档才挂全屏意图"这个契约 ——
注意这是"挂不挂"，不是"会不会盖住屏幕"，后者由系统按屏幕状态决定）。

#### 顺带补的清理

删除日程后，锁屏上的"脱敏版"通知（`channel=info`，和本体同 id）不会被系统一起清掉。
现在补发时的清扫把这一类也纳入了，避免一条已经删掉的提醒在锁屏上阴魂不散。

### v1.22 —— 提醒真的能叫到人了

两个需求：**只有时间没有日期的不建**；**提醒太无感，只有点进应用才察觉**。

第二个是大问题 —— 提醒不响，这个应用就没有存在的意义。所以先把三条故障在模拟器上实测出来，再动手改。

#### 故障一：提醒时刻已经过去，就永远不提醒

```
20:47  建一条 20:52 开始的日程（默认提前 10 分钟）
  → 提醒点 20:42 已过  →  旧代码直接 return  →  dumpsys alarm 里查无此闹钟
```

**这不是边角情况。** 从微信看到"三点开会"时往往已经两点五十了 —— 越紧急的事越容易漏。实测同一次里，20:52 那条没有任何闹钟，21:00 那条有。

修法：`ReminderPlan`（纯计算，11 条单测）把"提醒点已过但事还没开始"判成**立刻提醒**（2 秒后），而不是什么都不做。

顺带补上另一个洞：**全天日程从来没有提醒过** —— 旧代码 `if (!hasTime) return` 把这一类整个跳过了。现在全天日程在当天 9:00 提醒一次；如果那时已经过了（比如上午十点才建的）就立刻补一次，但**按"那天结束了"作废**而不是按 9:00 作废，否则十点建的"今天交材料"永远不响。

#### 故障二：通知被系统静音，因为它刷屏了

`dumpsys notification` 里的实据：

```
post_frequency{com.terry.smartschedule, count=150, muted=149/150, demoted=3}
```

150 条里 149 条被 Android 的通知限流判为刷屏并静音。原因是**每抓到一条日程就发一条"已自动记录"通知**。一旦被判定刷屏，连到点提醒也一起变哑。

修法：所有回执合并成**一条**通知（固定 id，只更新内容，`setOnlyAlertOnce`），渠道降到 LOW。到点提醒另走独立渠道，不受影响。

#### 故障三：提醒渠道不响不震

```
NotificationChannel{ mId='remind', mImportance=4, mVibrationEnabled=false, mVibration=null }
```

旧渠道只设了 `IMPORTANCE_HIGH`，**没设震动**。手机放兜里，一条不响不震的提醒等于没提醒。

这里有个坑：**通知渠道创建后属性就固定了**，代码里再改会被系统忽略。所以只能换 id 重建 —— 新渠道是 `remind_v2`：

| 属性 | 值 |
|---|---|
| 重要性 | HIGH |
| 声音 | 闹钟铃声，`USAGE_ALARM`（走闹钟音量，媒体音量为 0 也听得见） |
| 震动 | 两短一长 `0,300,200,300,200,700` |
| 灯 | 开 |

#### 加上全屏提醒页

光有通知不够 —— 正在上课或写代码的人不会去看通知栏。新增 `ReminderActivity`：

- 到点直接弹整页，**点亮屏幕、盖在锁屏上**（`setShowWhenLocked` + `setTurnScreenOn`）
- 时间用 72sp 大字，标题、地点依次
- 两个按钮：**知道了**（标记完成）、**稍后 10 分钟**（重新排闹钟）
- 一个「查看日程」跳进应用

要不要真弹全屏**由系统判断**（锁屏/息屏弹整页，你正在用手机时只出横幅）。这件事不该由应用猜 —— 实测用 `onPause` 记的"前台"标志在息屏时并不可靠：屏幕已经黑了，标志还是 true，于是该弹的时候没弹。这个标志最后整个删掉了。

#### 补发：漏掉的提醒补上

`catchUp()` 在打开应用和开机时跑一遍，把"该响但没响"的补发。判断依据就是 `ReminderPlan` 里"该立刻响"的那一档。

两个细节是踩出来的：

- **"已经响过"必须落盘**（`Prefs.remindedKeys`，键是 `事件id:开始时间戳`）。只放内存里的话，用户早上点了「稍后 10 分钟」、中午重进一次应用，立刻又弹一次 —— 他明确说了现在别烦他。
- 键里带开始时间戳，改了时间就自动算未提醒，不需要额外清理逻辑。

#### 顺手治的两个小毛病

- **提醒页显示上一条的内容**：`singleTop` 复用实例却没处理 `onNewIntent`。实测页面写着 21:05 的 TestC，实际响的是 21:16 的评审会。
- **点了「稍后」，通知还赖着不走**：`finish()` 在前、`lifecycleScope.launch` 在后，Activity 销毁时协程被取消，"撤通知"这一步时有时无。改成先干活再 `finish()`。

#### 需求一：只有时间没有日期的，不建

`CapturePolicy` 挡在入库之前：

| 原文 | 结果 |
|---|---|
| `下午3点去吃饭` | 拦 / 只有时间没有日期 |
| `17:30 打羽毛球` | 拦 / 只有时间没有日期 |


### v1.20 —— 认得出「27号」这种没写月份的日期

### v1.19 —— 只用正文识别 + 多选批量删除

**① 标题彻底退出识别**

上一版是"分辨哪些标题算内容、哪些不算"，为此叠了三轮规则：纯账号 → 会话名 → 纯日期群名（`12.31`）。每轮都是判完再扔，判错的代价很实在 —— 群名 `12.31` 的日期会盖掉正文明明写着的"明天下午3点"。

现在改成**标题连读都不读**：`SegmentPicker.pick()` 没有 title 参数，`extractSegments()` 也不再读 `EXTRA_TITLE` / `EXTRA_CONVERSATION_TITLE`。

这不是"再加一条规则"，是**结构性断掉** —— 那个字段根本进不来，判断再错也错不到这一步。顺带删掉了 `looksLikeSenderTitle` / `isPureDateLabel` 和它们依赖的三个正则，一共约 90 行。

之所以敢这么砍：能走到这里的通知全部来自微信 / QQ / TIM（见 `WatchedApps.kt`），这几个应用的标题永远是会话名。别人家的通知标题可能是内容，但我们不看别人家的。

**代价**：只有标题有内容、正文全空的通知解析不出来。微信/QQ 不存在这种通知 —— 真消息一定在 `EXTRA_MESSAGES` 或 `EXTRA_TEXT` 里。

**② 首页多选删除**

长按任意一条进入多选，顶部标题栏换成操作条：

```
← [返回]  已选 2 项              [全选]  [删除]
```

- 点卡片切换选中，再点一下取消；取消到一条不剩就自动退出多选
- 「全选」在全部选中时会变成「取消全选」
- 删除有二次确认，写明条数
- **返回键先退出多选**，不会一下把应用退掉
- 多选时输入卡和待确认横幅一起收起 —— 不然还能点「识别」叠出面板，状态就乱了

实现上有几个点不是随手写的：

| 关注点 | 做法 | 为什么 |
|---|---|---|
| 选中用什么标识 | 日程 **id**，不是列表位置 | 列表会因新通知随时刷新，位置会变 |
| 每次点选的重绘范围 | 只刷变化的那几条 | 全量重绑会让几十张 5 层玻璃卡片重绘，一下一下点会明显卡 |
| 删除顺序 | 先撤提醒和通知，再删库 | 反了就查不到 id，闹钟留在系统里继续响 |
| 删库方式 | 一个事务 + `IN (...)`，500 个一批 | 循环删会产生 N 次事务提交，中途失败还会删一半 |
| 勾选框位置 | 和「完成」框**叠在同一处**，互斥显示 | 并排会多占 40dp，一进多选文字重新折行，整屏看着跳一下 |

**交互变更有说清楚的地方**：长按原来是"删除这一条"，现在是"进入多选"。单条删除仍然在编辑面板里（点开卡片 → 左下角「删除」）。

### v1.18 —— 群名叫 `12.31` 的群被反复建成日程

两个层面的毛病，第二个比第一个严重得多。

**① 群名里的日期被当成日程日期**

微信群名可以就叫 `12.31`（跨年那几天建的群尤其常见）。这类标题里"确实有时间"，所以按老规则被判成内容，日期就取自群名。

**② 更糟的：群名盖掉了正文真正写的时间**

```

  → 建成 2026-12-31 15:00，置信度 90，直接自动入库
```

正文明明写着"明天下午3点"，日期却被群名抢走。**这条比误报难发现得多** —— 日程建出来了，时间也是"合法"的时分，只有用户自己记得原文才看得出错。

**根因：判断顺序错了。** 老逻辑先看"标题里有没有时间"，有就当内容。可群名本身就可能是个日期。

| 输入 | 剥掉时间后剩 | 结论 |
|---|---|---|
| `12.31` | 空 | 群名，丢掉 |
| `12.31(3条新消息)` | 空 | 群名，丢掉 |
| `10月25日` | 空 | 群名，丢掉 |
| `周三` | 空 | 群名，丢掉 |
| `12.31 学习小组` | `学习小组` | 有内容，但不是标题该放的东西 |
| `明天下午3点开会` | `开会` | 内容，保留 |

**③ 会话名有一条自己的泄漏路径**

`EXTRA_CONVERSATION_TITLE`（会话名）之前只在"有 MessagingStyle 消息"时才被跳过。没有消息体的群通知，群名会从这里直接混进正文 —— `12.31 学习小组` 这种非纯日期的群名就走这条路。

现在**会话名无条件不参与**：它的语义就是"哪个群/谁"，永远不是内容。

**④ 顺带把这块逻辑抽出来测了**

`extractSegments()` 要构造 `Notification` 对象，JVM 上做不到，所以这块一直没单测。标题规则到这一版已经改了三轮（纯账号 → 会话名 → 纯日期标签），每轮都是往同几行里加条件，很容易顾此失彼。

现在拆成 `SegmentPicker`（纯 Kotlin）+ 只负责读字段的 `extractSegments`，配 13 条单测，包含上面那个"日期被群名盖掉"的场景。

**一个刻意保留的区别待遇：** 正文里的纯时间不过滤。

「明天下午3点」单独发出来虽然只有时间、没写要做什么，但它是用户自己敲的待办（省略了动词），过滤掉会漏真实日程。**标题那个位置不该放内容，正文位置可以。**

### v1.14 —— 昵称被当日期、流量短信被当日程

两个真机误报，外加一类顺带处理的闲聊。

**① 微信昵称里的数字被当成日期**

```
12.31lyd：今天天气不错   →  建出 12 月 31 日的日程
```

`12.31lyd` 是昵称。点分日期的正则只排除了「前面紧邻字母」（挡 `v1.8`），没排除「**后面**紧跟字母」，于是 `12.31` 被当成 12 月 31 日。

**② 流量短信被建成日程**

```
您本月已使用流量8.5GB，剩余1.5GB，超出部分按0.29元/MB计费
```

`8.5` 被当成 8 月 5 日。这类文本里全是数字（流量、资费、金额），解析器必然从中捞出点什么。

修法是加一层资费类关键词识别（流量 / 话费 / 套餐 / 资费 / 元每MB …），命中且没有真实时间表达就放过。

**③ 顺带：只有模糊日期的闲聊**

```
阿伟：今天天气不错   →  建出"今天 全天：天气不错"
```

新加 `isSmallTalk()`：**只有**「今天/明天/周X」这类模糊词，没有明确时间点、没有绝对日期、没有事件词、也没有动作词 → 判为闲聊。

分寸是有意的：`李四：明天去北京` 因为有动作"去"仍然会建；`明天考试` 因为有事件词仍然会建。宁可漏掉少量模糊表达，也不要把聊天全建成日程。

### 一个很隐蔽的正则坑

修 ① 时，`RE_ABS_DATE` 的负向前瞻只写了 `(?![A-Za-z])`，结果**还是匹配上了** —— 因为 `\d{1,2}` 贪婪匹配 `31` 失败后会回溯成 `3`，此时前瞻看到的是后面的 `1`（数字不是字母）就通过了，`12.31lyd` 被匹配成 `2.3`。

必须写成 `(?![A-Za-z\d])`。**负向前瞻只排除字母不够，数字也得排除，否则回溯会缩短匹配绕过它。** 这条是单测抓出来的。

### v1.13 —— 待确认日程可以在通知栏直接确认

之前待确认的日程只发一条「需要确认」通知，想处理就得点开应用。现在通知上直接带两个按钮：

| 按钮 | 效果 |
|---|---|
| **确认** | 转正 + 按时间排提醒，通知消失 |
| **删除** | 直接丢掉，提醒和通知一起撤 |

实现上有四个地方必须做对：

1. **`autoCancel = false`** —— 这是一条待办，处理掉才该消失。点内容进应用也不该让它凭空不见，否则再回来就找不到「待确认」的入口了。
2. **按钮的 `requestCode` 按「日程 id + 动作」唯一**。全用同一个的话，系统会把多条日程的按钮当成同一个 PendingIntent，点哪条都作用在第一条上 —— 而且从通知栏完全看不出来，只有用户发现"确认了 A 结果 B 变了"才暴露。算法抽到 `NotificationIds`，配 5 条单测。
3. **`goAsync()`**：`onReceive` 跑在主线程且必须很快返回，而查库、排提醒都是 IO。别忘了 `finish()`。
4. **所有改动路径都要撤通知**：应用内确认、应用内删除、清空全部数据，都要调 `clearPending`，否则数据变了通知还挂着「需要确认」。

另外补了一条前台刷新：接收器处理完发一个本应用内广播，MainActivity 收到就 `reload()`。应用里操作和通知栏操作，看到的是同一份数据。

### v1.12 —— 拦住重复日程

手动添加**完全没有去重检查**。同一条内容走两遍「识别 → 添加」，就是两条日程。

之前只有通知自动抓取会查重（`existsSimilar`），手动流程和编辑流程都没查。

改法：

- `Repo.findSameEvent(title, startAt, excludeId, windowMs)` —— 返回撞上的那一条，不只是 `true/false`，这样提示能说清撞的是什么
- **新建时查**，窗口 1 分钟（选择器只能选到整分）
- **编辑时查，但排除自己** —— 否则只改个地点就会撞到自己
- 通知抓取沿用，窗口放宽到 5 分钟（推算出来的时间常差几分钟）

**分寸**：只拦「标题和时间都一样」的。同一时刻不同标题的日程仍然允许 —— 那可能是真并行的事（一边开会一边线上接入），硬拦反而是错的。

### v1.11 —— QQ 通知把发送人号码当成了标题

抓下来的日程标题是一串数字（对方的 QQ 号）。

根因两层：

1. `extractSegments` 把 `EXTRA_TITLE` 也当成了"候选段"。但聊天类通知（`MessagingStyle`）的标题是**会话名** —— 群名、联系人昵称，或者直接就是对方 QQ 号。把它拼进正文，日期被挖走之后，剩下的正是那串号码。
2. 某些通知的 `EXTRA_SUB_TEXT` / 会话标题也可能是账号。

修法：

| 层 | 做法 |
|---|---|
| 结构 | **有 `MessagingStyle` 消息时，标题不再当候选段** —— 这类通知的正文才是内容，标题只说明"谁发的" |
| 内容 | 所有候选段过一道 `TextFilter.looksLikeSenderId()`：纯数字 ≥6 位、带 `用户/QQ/wxid_` 前缀、字母数字混排且含数字，判为账号就丢掉 |

判断特意做得很保守：`3.15`、`2026`、`10.25` 这些日期年份形状**不能误伤**。`10.25` 一开始就被误判成账号了，是测试抓出来的。

**代价**：如果某条通知"只有标题里有时间、正文没时间"，现在会解析不出来。这种组合极罕见，比起标题变成一串号码，宁可漏掉。

### v1.10 —— 修"应用说连上了、通知栏说没连上"

**① 常驻通知只在启动那一刻算过一次状态**

`KeepAliveService` 的文案是在 `onStartCommand` 里生成的，之后**再也不更新**。而进程一启动，`App.onCreate` 先拉起常驻服务 —— 这时通知监听还没绑上，于是通知里永远写着"还没连上"；几秒后服务其实连上了，主界面也跟着变成"正在监听"。

同一件事，一个显示旧快照，一个显示实时值。

修法：

- `KeepAliveService.refresh()` 用同一个 id 更新通知
- `onListenerConnected` / `onListenerDisconnected` 各调一次
- 主界面每次刷新状态时也顺手调一次
- 状态判断抽成 `ListenerStatus` 枚举（`OFF` / `NO_PERMISSION` / `CONNECTING` / `RUNNING`），**主界面、设置页、通知栏共用一份**，不再各自写 if

**② "重新连接"时灵时不灵，其实是在自己打架**

`requestRebind` 每调一次就向系统发一次请求，而系统绑定是异步的：

- 点一两次 → 系统有时间完成 → 成功
- 点很多次 → 每次都打断上一次正在进行的绑定 → 反而一直失败

还有第二个来源：`MainActivity.onResume` 和 `SettingsActivity.onResume` **都会**自动发请求。你点按钮之前，可能已经有两三个请求在排队了。

修法：

| 改了什么 | 效果 |
|---|---|
| 手动点击**只发一次** | 按钮立刻变"正在连接…"并置灰 |
| 最多等 4.5 秒 | 期间再点不会发新请求 |
| 两个页面的 `onResume` 只观察、不发请求 | 不再和手动那次抢 |
| 主界面整个进程只自动请求一次 | 切页面不重复发 |
| 4.5 秒仍连不上 → 弹框 | 引导去系统设置关开授权（真正能强制重绑的只有这个） |

### v1.9 —— 修两个真机问题：误报 + 重连卡住

**① 下载完成通知被建成了日程**

原文是：`smart-schedule-v1.8-debug.apk.1 已保存至"文件管理/安装包"，点击查看。`

根因：点分日期的正则负向后顾只写了 `(?<![\d.])`，**没排除字母** —— 于是 `v1.8` 里的 `1.8` 被当成「1 月 8 日」。又因为 1 月 8 日今年已经过了，自动推到 2027 年，最终落成一条待确认日程，标题还被挖成 `smart-schedule-v -debug`。

两层修复：

| 层 | 做了什么 |
|---|---|
| 解析器 | 点分/斜杠日期前面不能紧邻字母：`v1.8`、`v2.0`、`1.8-debug` 不再当日期 |
| 通知层 | 新增 `TextFilter`：文件/系统类通知（已保存至、下载完成、安装包、带文件扩展名…）直接放过 |

通知层的判断有个分寸：**只要出现"明天/周X/几点"这类真实时间表达，仍然当日程处理**。「明天下午3点前把报告.docx发我」是个正常日程，不能因为带 `.docx` 就被丢掉。

顺带修了个旧 bug：`1.8-1.10` 这种点分区间，`8-1` 会被斜杠/短横线那条规则抢先匹配成「8 月 1 日」。

**② 重连一直显示"系统节流"**

不是系统的问题，是我自己的：

- `MainActivity.onResume` **每次**都会自动请求一次重绑
- 你切到设置页点按钮，正好落在 30 秒节流窗口里
- 于是永远返回 false → 提示"系统节流"

而且每切一次页面，节流起点又被刷新一次，你永远等不到窗口。

修复：

- **手动点击传 `force=true`** —— 你要的就是"现在再试一次"，不该被挡回去
- 节流 30 秒 → 5 秒，且只作用于自动调用
- 返回值从 `Boolean` 改成三态 `RebindResult`：`SENT` / `THROTTLED` / `FAILED`，提示能说清到底是哪种
- 新增入口「打开系统「通知使用权」设置」：`requestRebind` 只是**请求**，系统可以不理；**真正能强制重绑的是把开关关掉再打开**
- 设置页会显示「已请求重连 N 次」，一直失败时直接引导走系统设置那条路

### v1.8 —— 日程支持编辑

之前建完就改不了，想调个时间只能删掉重建。现在点一下就进编辑面板。

- 标题、日期、时间、全天、地点全都能改
- **点击行为变了**：以前点一下是「标记完成」，现在点一下是「编辑」。完成交给左边的勾选框 —— 它本来就在做这件事，同一个动作绑两处是浪费
- **编辑即确认**：待确认的条目改完保存就转正并排上提醒，不用再找确认按钮
- **改时间会复位完成状态**：一条已完成的事被推迟到别的时刻，说明它还没发生。只改标题或地点则保持原状态（否则改个错别字就变回未完成，很反直觉）

实现上识别结果面板和编辑面板共用一个 `createSheet()`，避免两套面板行为不一致 —— 比如"勾了全天就把时间按钮置灰"这种联动，只写一个入口漏另一个就是 bug。「改时间要不要复位」抽成 `EventEdit.shouldResetDone`，配 4 条单测。

### v1.7 —— 修"服务连上了但通知毫无反应"

三个真问题，第一个是主因。

**① 群聊通知的消息体根本没读。**
微信、QQ、短信这类聊天通知用的是 `MessagingStyle`，真正的消息内容存在 `EXTRA_MESSAGES`（Bundle 数组）里，`EXTRA_TEXT` 往往只是「3 条新消息」这种摘要。之前只读 `EXTRA_TEXT` —— 也就是说**群消息基本全部漏掉**，只有单条私聊偶尔能碰到。现在同时读 `EXTRA_MESSAGES` 和 `EXTRA_HISTORIC_MESSAGES`。

**② 多条消息被拼成一句话。**
「张三说哈哈哈 + 李四说明天下午3点开会 + 王五说收到」拼起来变成一句，解析器只取第一个日期，还容易被前后文干扰。改成**先整体、再逐段**：整体拼起来信息最全（标题只有时间、正文只有事件名时），整体不行再逐段试。这段策略抽成了 `SegmentParser`，配 7 条单测。

**③ "回调没进来"和"进来了被筛掉"在界面上长得一模一样。**
所有提前 return 的分支都不写日志，所以你看到的是"明明连着，什么都没发生"，完全无法定位。补了三样东西：

| 补的东西 | 在哪 | 作用 |
|---|---|---|
| `lastCallbackAt` | 主界面副标题 | 只要回调进来就更新，显示「最近收到通知 3 分钟前」。这是服务在工作的**唯一硬证据** |
| 诊断模式 | 设置 → 通知诊断 | 打开后每个回调都记一条（**仍不记正文**），能看出卡在哪一步：文本太短 / 常驻通知 / 折叠摘要 / 不含时间线索 |
| 立即检测当前通知栏 | 设置 → 通知诊断 | 把通知栏里**已有**的通知过一遍，不用干等新通知。验证管道通不通最快 |

**顺带修的文案 bug**：设置页最底下那个按钮复用了 `action_save`（值是「添加到日程」），所以设置页底部一直挂着一个莫名其妙的「添加到日程」。改成独立的「保存设置」。

### v1.6 —— 退到后台后禁止截屏

只加一条：切到后台时窗口自动上 `FLAG_SECURE`，回到前台立刻放开。

- **在前台**：截图、录屏、屏幕共享都正常，把日程发给同学不受影响
- **切到后台**：最近任务里的缩略图变成空白，别人拿起手机翻不到你的日程
- **锁屏**：本来就是脱敏通知（v1.5）

为什么不做成"全程禁止"：`FLAG_SECURE` 是一刀切的，全程开会连用户自己按电源键截图也是黑屏，而日程截图分享是这个应用里很自然的动作。

实现挂在 `Application` 的 `ActivityLifecycleCallbacks`（`util/ScreenGuard.kt`），不是每个 Activity 各写一遍 —— 这样以后新增页面不会漏。

**挡不住的**：另一台手机对着屏幕拍、root 后抓显存。这是 Android 应用层的天花板。

### v1.5 —— 安全加固：不留口子，不该留的数据不留

完整清单见 `docs/security-review.html`。核心是两件事：**把能被外部利用的面收掉**，**把为了排查顺手存下来的隐私删掉**。

- **API Key 不再明文落盘**：改用 Android Keystore 的 AES-GCM 加密，老明文自动迁移删除
- **关掉数据外流通道**：`allowBackup=false`（原来 `adb backup` 能一条命令导出全部数据）、云备份/换机迁移排除全部数据
- **禁止明文 HTTP**：原来用户填 `http://` 地址时，通知原文和 API Key 会明文走网络。现在只放行本机回环地址
- **抓取日志默认不存通知原文**：原来存每条前 160 字（可能是聊天内容、验证码、订单号）。现在只记"哪个应用、什么结果、为什么"，需要排查时再临时打开
- **通知自动抓取默认不调大模型**：原来开了大模型后，后台每条通知都会把原文发到第三方。现在拆成两个开关
- **锁屏不显示日程内容**：设为 `VISIBILITY_PRIVATE`，锁屏只看得到"智汇日程"，解锁后才是具体内容
- **收掉多余导出组件**：移除 profileinstaller 带进来的对外 receiver，现在只剩桌面入口一个导出组件

### v1.4 —— 修"退出重进还是显示服务没连上"

真机上反馈：完全退出应用再进去，顶部显示服务没连上，按提示退出重进也没用。查出两个叠加原因：

1. **原来没有任何"重连"动作**。设置页那个按钮只要授权成功就永久变灰，主界面却提示"点右上角修复"——点进去是个灰按钮，死路。
2. **状态是进程内变量**，进程被杀后必然为 false；系统重新绑定监听服务需要时间，而界面只在 `onResume` 查一次状态，之后不再刷新，于是一直停在"没连上"。

修法：加 `ServiceHealth.requestRebind()`（带 30 秒节流，系统对重绑有频率限制）；主界面和设置页在"已授权但未连接"时主动催一次，并在 1.2 秒后复查状态；按钮改成三态（去授权 / 重新连接监听服务 / 通知监听正常）。

文案也改了：以前直接说"已断开"，现在"已授权但还没连上"显示为"正在等待系统连接…"——这是正常过渡态，不该吓人。

### v1.1 —— 修上一版真机反馈的三个问题

1 识别不到 / 后台没保活，2 日期识别错了却照生成，3 顶部 UI 压状态栏且难看。

### 1. 自动添加"有时候识别不到" + "后台没保活"

**根因有四个，全修了：**

| 问题 | 原因 | 现在 |
|---|---|---|
| 通知静默消失 | 置信度不到 85 且没开大模型时，`return` 直接丢弃，什么都不留 | 拆成三档：有把握直接建；没把握进**待确认**；连日期都解析不出才记「跳过」，并且**写进日志** |
| 粗筛把正常通知挡了 | 前置筛选要求文本含「点时日月周分号」，`明天开会`、`后天答辩` 这类**纯中文相对时间全被丢掉** | 筛选放宽：有数字、有时间信号、有日程类词（开会/提交/截止…）任一项就放行 |
| 去重过头 | 用 SharedPreferences 存"最后一条签名"，被后续通知覆盖后同一文本又重复处理 | 换成内存 LRU（32 条），10 分钟窗口，不落盘 |
| 服务被杀后不回来 | 没有任何重连机制 | `onListenerDisconnected` 里主动 `requestRebind()` |

**保活做了四层，但先说清楚——Android 上没有"绝对保活"：**

1. **前台服务**（`KeepAliveService`）—— 把进程优先级抬到前台级，通知栏会有一条常驻提示，可在设置里关
2. **`onListenerDisconnected` 重绑** —— ROM 断开监听后主动要求系统重新绑定
3. **电池优化白名单** —— 设置页一键申请，这是国产 ROM 上最关键的一步
4. **自启动引导** —— 按小米/华为/OPPO/vivo/三星/魅族逐个尝试跳转对应管理页，跳不进去给文字指引

要真正做到"一直在跑"，前三层（尤其第 3 层）都得开。系统内存紧张时仍可能被杀，这是 Android 的设计，代码顶不住。

### 2. 日期识别错了却照样生成

**现在的原则：能推算的要标明是推算的，算错了要报出来，拿不准的不许自动入库。**

解析结果新增两个字段：

- `dateSource` —— 日期从哪来：`ABS`（原文写死）/ `REL`（明天、3天后）/ `WEEK`（周X 推算）/ `TIME_ONLY`（只有时间）/ `NONE`
- `warnings` —— 每条需要你核对的问题，非空就**强制进待确认**

会触发警告的情况：

| 情况 | 提示 |
|---|---|
| 原文日期和星期对不上 | 「原文写的是 10月26日（周一），但同一段里还提到了「周日」，两者对不上，请核对到底是哪天」 |
| 只有「周X」没写日期 | 「「周三」是推算出来的，我按 10月28日（周三）算的，不对请手动改」 |
| 「周X」就是今天 | 同上，并且明确说"就是今天" |
| 只有时间没日期 | 「原文没写日期，只写了时间，我按今天（10月23日（周五））算的」 |
| 没写年份且今年已过 | 「原文没写年份，3月5日 今年已经过了，我按 2027 年算的」 |
| 算出来的日期已经过去 | 「算出来的日期 10月19日（周一）已经过了，确认一下是不是把月份搞错了」 |
| 日期在 180 天以外 | 「如果原文是活动周期而不是某一天，请手动改」 |

**可信度分级直接决定落地方式：**

| 日期来源 | +具体时间 | 处理 |
|---|---|---|
| 原文写死 | 是 → 90 分 | 自动入库 + 排提醒 |
| 明天/后天/N天后 | 是 → 85 分 | 自动入库 |
| **周X 推算** | 是 → 70 分 | **一律进待确认**，用户点头才转正 |
| 只有时间 | 60 分 | 待确认 |
| 原文写死但没时间 | 55 分 | 待确认（全天日程要你自己看） |

待确认的日程**不排提醒**，列表里置顶、橙色边框、带「待确认」标签，点一下进编辑面板（能看到时间、为什么拿不准、原文），核对完保存就转正。

### 3. 顶部 UI 和状态栏重叠 + 不好看

**重叠的根因**：`targetSdk = 35`，Android 15 起强制 edge-to-edge，`android:statusBarColor` 直接失效。上一版还在主题里设 `statusBarColor`，等于没设。

**修法**：`WindowCompat.setDecorFitsSystemWindows(window, false)` + 读 `WindowInsets` 把状态栏高度写进头部占位 View，底部列表加导航栏 padding。不是靠主题糊。

**界面重做（v1.2 亚克力版）**：

旧版是「深绿渐变条 + 不透明白卡片」，视觉上就是普通模板 App。现在整套换成亚克力（磨砂玻璃）质感。

亚克力的观感不是靠一张半透明色块就能出来的，是四层叠出来的，缺一层就退化成「蒙了层白纱」：

| 层 | 作用 | 在哪 |
|---|---|---|
| ① 光斑背景 | 亚克力得有东西可透。纯色底 + 半透明白 = 一块灰白方块 | `view_acrylic_bg.xml` + `blob_*.xml` |
| ② 半透明白面板 | 主体，80% 白，背景色能透上来 | `bg_acrylic_card.xml` 第 2 层 |
| ③ 顶部反光 | 上亮下透的竖向渐变，玻璃斜向高光 | 同上第 3 层 |
| ④ 噪点颗粒 | **亚克力和「半透明色块」的唯一区别就在这** | `noise_tile.png`（128×128 平铺） |

其他配套：

- **头部改成贴顶的磨砂条**，不再是深色渐变；标题改深色，状态栏图标切成深色（`windowLightStatusBar = true`）
- 面板边缘是 1dp 竖向渐变高光（顶边亮、底边几乎透明），不是实心描边
- 主按钮：蓝→亮蓝渐变（`#2563EB → #4F8EF7`）+ 顶部反光 + 圆角水波
- 日期分组头加小竖条；时间列右侧竖线两端渐隐，比实心线干净
- 待确认项整块玻璃换暖色（琥珀边 + 暖白主体），不是只加个橙框
- 底部弹层背景换成 `bg_acrylic_sheet`，和主界面同一套材质

**为什么不做真高斯模糊**：Android 上要模糊「背后」的内容只能截屏再模糊，跨应用做不到，实时也吃不消。光斑本身就是柔边渐隐的，视觉上等价于模糊过的壁纸，代价接近零。

⚠️ 没有 `elevation` 投影：`layer-list` 只能给出矩形 outline，加了会变成圆角卡片背后挂一个方影子，非常脏。层次全靠高光边和透明度拉开。

## 识别不到怎么办（排查手册）

主界面副标题 → 设置页状态 → **查看最近的通知处理记录**，三层能定位到具体环节：

| 现象 | 说明 |
|---|---|
| 日志里完全没有某条通知 | 服务没在跑。看副标题：未授权 / 已断开 |
| 日志里有，结果是「已跳过」 | 说明收到了但没识别出时间。详情里写了原因，把那段原文拿来我加规则 |
| 日志里有，结果是「待确认」 | 正常，去列表里点开那条保存一下就转正 |
| 设置页反复提示连不上，点了好几次"重新连接" | 令牌被系统摘掉了。用设置页那行「打开系统「通知使用权」设置」，把「智汇日程」的开关**关掉再打开**；还不行就重启手机 |
| 日志里「已经有一条一样的日程了」 | 去重命中，10 分钟内同文本只处理一次 |

`已跳过` 的典型原因：
- 通知里确实没有时间信息（如"作业已提交"）
- 只有日期没有时间 → 会进待确认，不算跳过
- 文本太短（少于 4 个字）

## 隐私与安全

所有数据只在本机，不联网，不参与云备份，一键可删。

| 数据 | 存在哪 | 加密 | 说明 |
|---|---|---|---|
| 日程（标题/时间/地点/原文摘要） | 本机 SQLite | 应用私有目录 | 原文摘要截断 500 字 |
| 通知处理日志 | SharedPreferences | 否 | **默认不含通知正文**，只记"哪个应用、什么结果、为什么" |

- 抓取日志默认不存通知原文；排查问题时可在设置里临时打开「记录通知原文」
- 所有解析都在本机完成；应用没有网络权限（Manifest 里没有 INTERNET），原文不会离开设备
- 锁屏只显示"智汇日程"，不显示日程标题
- **退到后台后，最近任务的缩略图是空白**（`FLAG_SECURE`），回到前台即可正常截图
- 设置页底部有「删除所有本地数据」，删完不留痕

⚠️ **debug 包（仅本机调试）的边界**：v1.28 起 debug 也关闭了 `debuggable`，
`adb run-as`、调试器附加都进不去。剩下的区别是签名：debug 用 SDK 自带的公开密钥库
（密码就是 `android`），任何人都能做出同签名包；release 用项目私有 keystore。
所以对外分发只用 release。

## 打包与签名

### 一条命令出包

```bash
./pack.sh release  # 发布用（GitHub Releases 只上传这个）
./pack.sh          # 本机调试用，不上传
./pack.sh all      # 两个都出（一般不用）
```

> **约定（2026-11-20 起）：GitHub Releases 只上传 release 变体；debug 包只留在本机调试。**
> 两种签名不同、不能覆盖安装，切换会丢日程数据。本机验证可以用 debug，
> 但对外的安装包统一用 release。

**签名配置一直保持可用**（keystore 和 `signingConfigs` 都在），`./pack.sh release` 一条命令就行。

产物自动按版本号命名，版本号从 `app/build.gradle.kts` 里读：

```
dist/smart-schedule-v1.19-debug.apk
```

出 release 时会多一个 `dist/smart-schedule-v1.9-release.apk`。

### 历史包怎么管

`dist/` 是**归档目录，历史包不删**。回滚、对比、定位"哪一版开始出的问题"都要靠它们。

`dist/HISTORY.md` 由打包脚本自动维护（同版本同变体重复打包不会重复记一行），
里面有一张表记录每个包的版本/versionCode/时间/大小，下面还有一份「各版本一句话」的改动索引 ——
堆到十几个包之后，光看文件名是分不清的。

当前归档：v1.0 · v1.3 · v1.6 · v1.7 · v1.8 · v1.9 · v1.10 · v1.11 · v1.12 · v1.13 · v1.14 · v1.15 · v1.16 · v1.17 · v1.18 · v1.19 · v1.20 · v1.21 · v1.22 · v1.23 · v1.24。
**v1.1、v1.2、v1.4、v1.5 没有留存** —— 那几次没保存产物，补不回来了。

同版本号重新打包会**覆盖**同名文件。这是对的：没升版本号就应该是同一份产物。
要留痕就升 `versionCode` + `versionName`。

### 签名材料放在哪

| 文件 | 内容 | 要不要备份 |
|---|---|---|
| `keystore/release.keystore` | 私钥（RSA 2048，10000 天有效） | **必须**，丢了就永远无法更新这个应用 |
| `keystore.properties` | 别名与密码 | **必须**，和上面那个一起 |

两个都在 `.gitignore` 里，不会进版本库。`app/build.gradle.kts` 从这个 properties 读签名信息，所以密码没有硬编码在代码里。

证书：`CN=Terry, OU=Personal, O=Personal, L=Guangzhou, ST=Guangdong, C=CN`
SHA-256 指纹：`B2:F9:1C:CC:CE:C5:79:DD:8A:37:E4:B0:1B:6D:58:54:75:67:58:D8:D8:8E:6E:57:52:9A:A9:A1:B9:A2:CE:B6`

### debug 包和 release 包的区别

| | debug | release |
|---|---|---|
| `debuggable` | false | false |
| 签名 | SDK 公共密钥（密码 `android`） | 自己的私钥 |
| `adb run-as` 读私有目录 | 拒绝 | 拒绝 |
| 调试器附加 | 不能 | 不能 |
| 伪造同签名更新包 | **能** | 不能 |
| 体积 | 4.8MB | 4.8MB |

### 装 release 包之前必须知道

**release 包和旧的 debug 包签名不同，不能覆盖安装。** 从 debug 切换过来必须先卸载 ——
而卸载会把日程库一起删掉。目前还没做导出/导入功能，日程重要的话先手动记一下。

从 v1.62 release 起，后续版本都用同一把 release 签名，升级可以直接覆盖。

### 为什么没开 R8 混淆

没有真机验证过的混淆配置等于埋雷：反射、Kotlin 协程、Android Keystore 任何一处被裁掉都是运行时崩溃，而且**只在 release 包出现**，debug 包完全正常，最难查。

release 的核心收益（`debuggable=false` + 私有签名）不依赖混淆。等有真机回归条件了再单独开。

## 已知限制

1. **起止区间只取起点**：「10月16日—10月26日」记 10-16；「19:00-22:30」记 19:00（区间会整段从标题里剔除，但只存起点）。
2. **一段话有多个日期只取第一个**：「周三或周四」按周三算，而且第二个"周四"也会被当成日期残渣清掉。活动周期 + 报名截止混在一段的公告，需要你在预览里确认取哪个。
3. **只有「下午/晚上」没有钟点** → 存全天，不瞎猜钟点。
4. **长通告的标题靠启发式**：优先取开头 `【】`，其次取带事件词的句子。整句只有一个日期的（"本周日上午"）会只剩"上午"这类没意义的标题。
5. **不支持的相对时间**：「1小时后」「半小时后」「月底前」「春节前」都解析不出来（只支持 今天/明天/后天/N天后/周X）。这类通知会在抓取日志里记成"没识别出日期时间"。
6. **通知监听只覆盖微信 / QQ / TIM**：其他应用的通知不分析（见 v1.17）。这类日程可以用输入框手动粘贴识别。
7. **通知监听只能读通知栏里显示的文字**：读不到聊天记录里的历史消息；图片、语音、文件类消息通知里没有文字内容，也就无从解析。多条消息合并的群通知只取最近 4 条。
7. **保活不是绝对的**，见上文。
8. **对话框还是 Material 纯白**：设置里的确认框、待确认核对框没跟亚克力统一，属于遗留视觉问题。
9. **切换签名会丢数据**：debug 包和 release 包签名不同，不能互相覆盖安装，卸载会删掉日程库。目前没有导出/导入功能。

### 验证工具：通知模拟器

`tools/notify-sim/` 是一个独立的最小工程（纯 Java、零依赖），专门用来在模拟器上
